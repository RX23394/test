# 知识库语料规划

本文档说明 Network RAG 的知识库定位、现有语料、补充清单与格式规范。

知识库面向**个人项目展示**：语料规模不求大，但要求主题完整、中文可问、引用可核对。
演示时最常见的提问是「TCP 三次握手」「VLAN 和 Trunk 区别」「OSPF 和 BGP 区别」
「IPv6 地址类型」这类基础题，因此**基础协议必须无死角**，冷门专题可以完全不放。

## 一、现有语料

7 篇纯文本 RFC，共约 915 KB、562 个切块（`backend/network_rag.db`）：

| 文档 | 主题 | 切块数 |
| --- | --- | --- |
| RFC768_UDP.txt | UDP | 3 |
| RFC826_ARP.txt | ARP | 15 |
| RFC1034_DNS_Concepts.txt | DNS 概念 | 76 |
| RFC1035_DNS_Implementation.txt | DNS 实现 | 75 |
| RFC1918_Private_IPv4.txt | 私有地址 | 13 |
| RFC2131_DHCP.txt | DHCP | 71 |
| RFC2328_OSPFv2.txt | OSPFv2 | 309 |

已知不足：

- **传输层几乎空白**：只有 UDP，没有 TCP。
- **链路层全部空白**：没有以太网、VLAN、STP。
- **路由只有 OSPF**：没有 BGP，没有路由策略与重分发。
- **无 IPv6**、无 NAT、无运维协议（NTP/SNMP/Syslog/VRRP）。
- **无中文语料、无厂商配置文档**，与中文提问方式不匹配。
- **`section` 元数据基本为空**：562 个切块中 422 个为 `NULL`，因为 RFC 纯文本没有
  Markdown 标题，`ChunkService` 无法按标题切分，引用只能落到「文档 + 页码」。
  已备好的新语料全部为带标题的 Markdown，`section` 覆盖率为 100%，可解决该问题。

## 二、补充清单

按演示价值排序。目标总量 **12–18 篇 / 150 万字左右 / 1500–2500 个切块**，
再多不会让演示更好，只会拉长索引时间并稀释检索精度。

RFC 正文通过 `.runtime/rfc_to_markdown.py` 转换为 Markdown：剥离分页页眉页脚与封面块，
把 RFC 自身的 `1.` / `2.1.` 编号（老 RFC 则用「顶格 + 后接空行」的样式）提升为
`##` / `###` 标题，RFC 792 与 4861 的标题因封面版式特殊而人工指定。

**首块不要放元数据或文档标题。** 实测把元数据/标题单独放在文档开头时会自成一块
（`section` 为空），并因为含协议名与来源链接而抬高向量相似度，把「IPv6 有哪几种
地址类型？」这类问题的 Top1 挤成无关的元数据块。现在的做法是：转换时直接丢弃
RFC 封面块，来源信息只保留在文件名里；厂商文档与内部文档的版本信息写进小节正文。

**仍未完成**：P0 中的华为与 Cisco 厂商配置指南（PDF）；P1、P2、P3 全部。

### P2 中文语料（对中文问答提升最明显）

- **自编中文教程**：把 P0 的英文协议改写成中文问答笔记，成本低、演示效果好。
- **厂商官方中文文档**：华为《HCIA-Datacom 学习指南》、H3C 配置指导、锐捷配置手册 PDF。
- **公开教学资料**：CCNA 学习指南中文版等（**注意版权，仅本地演示、不随仓库分发**）。

> 中文语料的价值不只是"能读懂"：检索是向量 + jieba 关键词的混合（RRF 融合），
> **中文术语只存在于中文语料里，关键词通路对英文语料完全打不通**。实测在只收录
> 英文 RFC 的语料上提问「TCP 三次握手的过程是怎样的？」，FTS5 对 `三次握手`、
> `拥塞控制`、`地址转换` 均为 **0 命中**——因为语料里根本没有这些中文词；此时只能
> 靠向量通路跨语言召回，而向量分数普遍贴着 `RETRIEVAL_MIN_SCORE=0.87` 的下限，
> 排序不稳定。**每补一个英文标准，最好配一篇同主题的中文笔记。**

### P3 自编私有文档（体现业务落地能力）

自编语料最能说明"这套系统能用在真实运维场景"，且完全没有版权风险：

- `网络拓扑说明.md`——设备、链路、区域划分
- `IP 地址规划表.md`——网段、VLAN、网关、用途
- `故障处理 SOP.md`——常见故障现象与排查步骤
- `变更与割接流程.md`——审批、窗口、回滚

## 三、格式规范

### 1. 文档头元数据

元数据必须放在**某个 `##` 小节之内**，否则它会自成一块、`section` 为空，
并在检索时与真正的正文争抢 Top8。整篇文档的第一块只能是元数据时，用 HTML
注释承载来源信息（注释并入首块，但不占独立块）：

```markdown
<!--
文档标题: RFC 9293 Transmission Control Protocol (TCP)
来源: https://www.rfc-editor.org/rfc/rfc9293.html
文档类型: 标准
更新日期: 2026-01
-->

## 摘要

...
```

若希望元数据出现在引用里，就把它写进小节正文：

```markdown
## 配置示例（适用 VRP V200R019）

- 适用版本: VRP V200R019
- 来源: 华为官方配置指南

...
```

**不要用 `#` 一级标题写文档名。** 它既不携带正文，又会成为独立切块：实测在
「IPv6 有哪几种地址类型？」这类问题上，标题块会被向量检索排在真正的正文之前。

### 2. 格式优先级

1. **Markdown（首选）**：`MarkdownParser` 将整篇读为一页，`ChunkService` 再按 `##`
   标题切块并填充 `section` 字段。已备好的 12 篇语料实测 `section` 覆盖率为
   96.9%–100%（唯一的空值来自承载元数据的首块），引用可从「文档 + 页码」
   升级为「文档 + 章节」。
   RFC 官方**只发布 `.txt` 与 `.html`，没有 Markdown 源**；`.runtime/rfc_to_markdown.py`
   负责把 `.txt` 转换过来（剥离分页页眉页脚、把 RFC 自身的编号提升为标题）。
2. **PDF（次选）**：页码是真实页号，引用体验好；仅支持文本型 PDF，扫描件会解析出空页。
   **按章拆分上传**，避免整本手册（900 页）破坏检索精度。
3. **DOCX**：先转换为 Markdown，保留标题层级。
4. **TXT（兜底）**：不携带结构信息，只用于无法转换的场景。

### 3. 命名规范

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 官方标准 | `RFC<编号>_<主题>.<ext>` | `RFC9293_TCP.md` |
| 厂商文档 | `<厂商>_<产品线>_<主题>_<版本>.<ext>` | `Huawei_S5700_VLAN配置_V200R019.md` |
| 自编笔记 | `<主题>_<类型>.<ext>` | `VLAN与Trunk_自编笔记.md` |

中文文档保留中文文件名，便于人工核对引用来源。

### 4. 切块规模

当前参数为**目标 320 embedding token、重叠 48、硬上限 450**，边界严格控制在
编码器 512 token 窗口内（实测最大值 320–324）。

> **尺寸必须用 Embedding 的分词器来量。** 历史上用 cl100k 计数并设上限 400，
> 而 `intfloat/multilingual-e5-small` 自己的分词器对 ASCII 密集文本（RFC 里的
> `+-+-+-+-+` 图、表格、参考文献列表）会数出 3–5 倍甚至更多 token：
> 实测有切块 cl100k 只有 290，编码器却要 901，直接导致索引失败
> （`EmbeddingInputTooLongError`）。该缺陷已修复，详见
> `backend/app/services/token_counter.py`。

- 单篇建议 **3k–20k 字或 20–60 页**；超过则按章拆分。
- 单个小节控制在 1–2 个切块内，避免答案被截断在两块之间。
- 单文件上限由 `DOCUMENT_MAX_UPLOAD_BYTES` 控制（默认 50 MB），不是瓶颈，
  检索精度才是。
- 一份 300 页的 RFC 会切出 200–300 块，属正常范围。

## 四、演示效果保障

补完语料后建议做一轮可复现评测，把结果写进 README——这是个人项目展示里
最有说服力的一页，比"收录了 N 篇文档"更硬：

1. 准备 20 个真实问题集（链路层 4 / 路由 5 / 传输层 3 / IPv6 3 / 运维 3 / 中文提问 2），
   每题标注期望命中的文档与章节。
2. 指标：**Top8 召回率**、**「知识库没有足够资料」的误拒率**、平均响应延迟。
3. `RETRIEVAL_MIN_SCORE` 是关键旋钮：语料噪音变多时，
   阈值过高会把有效内容挡在 prompt 之外，表现为"明明收录了却答'没有足够资料'"。
4. 切块参数变更后需重新索引——已索引文档不会自动重切，
   `rebuild_search_index` 只重新分词、不重新解析。

### 已实测的检索行为（重要）

补完语料后跑了一轮中文提问的真实检索，结论如下：

| 现象 | 测量结果 | 原因 |
| --- | --- | --- |
| 中文关键词命中 | 「三次握手」4 命中、「拥塞控制」5 命中、「根桥选举」3 命中 | 中文语料到位后 jieba + FTS5 通路才可用 |
| 中文问英文语料 | 相关与无关候选的向量分数**全部挤在 0.85–0.87**，差值常小于 0.002 | multilingual-e5-small 的跨语言区分度不足 |
| 排序结果 | 「IPv6 有哪几种地址类型？」中，TCP 报文结构（0.8701）**略高于** IPv6 地址架构（0.8686），无关块被排到第一 | 上述窄带分数 + RRF 按排名融合，微弱差距被放大 |

三点待办，按性价比排序：

1. **给英文标准配中文笔记**（如 IPv6 地址类型、NAT）。语言对齐后关键词通路参与，
   分数差距从"噪声级"变成可判别，这是成本最低、收益最确定的一步。
2. **修正 `RETRIEVAL_MIN_SCORE` 的配置漂移**：`README.md` 与 `.env.example` 写的是
   `0.87`，实际 `.env` 里是 `0.8`。阈值落在跨语言分数带正中间（0.85–0.87）时，
   少量无关块会稳定混入 Top8，应把两者对齐并在评测里定标。
3. **换更强的向量模型**（如 `multilingual-e5-base`/`large`）或对中英文分别检索后再融合。
   这一步会改变 `EMBEDDING_DIMENSION`，需要重建集合与全量重索引。

## 五、授权注意

- RFC 文本可自由分发，但应以链接形式标注来源。
- IEEE 标准、厂商手册、教材**不要随仓库分发**，仅本地演示使用；
  `.gitignore` 已排除 `data/uploads/`，自编语料如需公开请单独确认。
- 个人项目公开展示时，README 中说明语料来源与授权状态即可。
